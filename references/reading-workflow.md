# Book Wiki 共读流程

这是 Book Wiki Reader skill 的核心工作流。

## 核心原则

1. 先判断用途，再决定读法。不默认每本书都值得深读。
2. 先检视，再共读。先给读者看书籍介绍、目录、骨架地图和阅读建议。这里的“看”是前台展示，不是只写入文件。
3. 共读以问题块或观点块为单位，不被章节绑架。章节只是定位工具。
4. AI 先读解，读者再赋义。AI 负责把书读清楚，读者负责确认什么对自己重要。
5. 提问要触发思考，不制造负担。每个阅读单元只问一个具体问题，并在问题后停下来等用户回应。
6. 作者观点、AI 判断、用户观点分开记录。
7. 只保存未来会被调用的东西。Wiki 不是摘要仓库。
8. raw 来源可追溯，整理后的 wiki 内容能回到来源。
9. 长书必须分层处理。不要把整本书一次性塞进上下文，先建索引，再用 context stacking 保留多层压缩结果。

## 前台输出契约

Book Wiki Reader 的第一原则是：用户必须在对话里直接看到阅读地图。文件、附件、wiki 写入都是备份，不是前台体验本身。

当用户说“开始读”“按 Book Wiki 读”“继续读这本书”时，第一次进入阅读流程的回复必须包含：

- **一句话简介**：这本书是什么。
- **原始目录或目录摘要**：如果目录很长，可以先展示一级/二级目录；如果没提取到目录，必须说明原因。
- **初版骨架**：3-7 条，说明问题、主线、部分关系和推进方式。
- **核心问题**：这本书主要想回答什么。
- **章节/单元价值判断**：哪些是主干、案例、背景、可跳读或待确认。
- **阅读建议**：建议从哪里开始，以及为什么。
- **下一步问题**：让用户选择读法或确认第一单元。

禁止只输出：

- “我已经生成阅读地图并入库”
- “请打开附件查看”
- 只有一句话简介就开始共读
- 直接进入第一章/第一单元而不展示目录和骨架

如果已经生成了 `reading-map-initial.md` 或其他文件，也要把其中最关键的目录、骨架和建议压缩后贴到聊天正文中。

## 目录分工

- `raw/books/`：书籍原文件、来源记录、转换后的文本。
- `raw/books/<book-slug>/chunks/`：长文本分块，用于检视和共读时按需读取。
- `raw/books/<book-slug>/chunk-index.md`：分块索引，用于定位而不是阅读全文。
- `raw/books/<book-slug>/stack/`：分层上下文，包括 chunk 摘要、章节摘要、问题块摘要和全书骨架。
- `raw/inbox/`：临时摘录、截图、链接、转录文本、零散想法。
- `wiki/books/`：单本书笔记。
- `wiki/themes/`：跨书主题卡。
- `wiki/ideas/`：阅读中产生的想法、项目、方法和判断。
- `wiki/authors/`：重要作者卡。
- `wiki/reading-plans/`：阅读计划、书单和学习路线。

## 0. 入库

用户提供书籍或相关材料后，先保存来源。

记录：

- 书名、作者、版本或语言
- 用户提供的文件路径或链接
- 导入日期
- 原文件或原始文本位置

产物：

- `raw/books/<book-slug>/source.md`
- `raw/books/<book-slug>/chunk-index.md`
- `raw/books/<book-slug>/chunks/chunk-0001.md` 等分块文件
- 原文件或转换文本归档到 `raw/books/<book-slug>/`
- 初始化 `wiki/books/<book-slug>.md`

长书入库规则：

- 原文件只做归档，不直接进入上下文。
- 纯文本或 Markdown 应切成约 8000 字符一块，并生成 `chunk-index.md`。
- 非文本文件先转换成可读文本，再对转换文本分块。
- 后续所有阅读动作优先读取索引，再按需要读取少量分块。

## Context Stacking

Context stacking 是长书阅读的默认策略。目标是在少消耗 token 的同时，尽量不丢失重要信息。

它不是魔法，也不是说 AI 可以不读文本就准确理解全书。它把阅读成本拆成两种：

- **快速检视**：不扫全文，只读目录、前言、结论、章节首尾和少量关键分块，生成“初版骨架”。成本低、速度快，但结论必须标注为暂定。
- **全书索引**：顺序读取所有 chunks，每次读一小块，压缩进 stack 后释放原文上下文，最后用所有分块摘要校准全书骨架。总 token 成本更高，但只需要建立一次，后续可以复用。

因此，context stacking 省 token 的地方不是“第一次完全不读”，而是“不让全文同时进入上下文，并且避免后续反复读全文”。

从低到高分成五层：

1. **原文层**：`original/` 和 `chunks/`。只在需要核对证据、例子、定义或措辞时读取。
2. **分块摘要层**：每个 chunk 读完后压缩成 5-10 条要点，记录关键概念、主张、例子和位置。
3. **阅读单元层**：把多个 chunk 合并成一个问题块、观点块、论证块或方法块。
4. **章节/部分层**：压缩这一部分解决的问题、作者答案、论证路线、关键例子、可跳读内容。
5. **全书骨架层**：全书核心问题、主线、主要观点、薄弱点、与用户相关的资产。

每次共读时，优先带入高层上下文：

- 全书骨架
- 当前章节/部分摘要
- 当前阅读单元摘要
- 用户阅读意图和已确认观点

只有当出现以下情况时，才下钻到原文层：

- 用户要求看证据或原文依据
- AI 对一个观点不确定
- 需要判断作者的论证是否成立
- 需要保留短摘录
- 需要纠正上一层摘要可能造成的信息损失

每读完一个单元，都要更新 stack，而不是一直依赖对话历史。这样即使上下文被压缩或换新会话，也可以从文件恢复阅读状态。

### 骨架可信度

全书骨架必须标注生成方式和可信度：

- **初版骨架**：基于目录、前言、结论、章节首尾、抽样分块生成。适合决定值不值得读、怎么读，但不能当最终理解。
- **校准骨架**：基于全书 chunk 摘要生成。适合做全书总结、主题卡分流和跨书比较。
- **修订骨架**：在正式共读和用户讨论后更新，包含用户确认、不同意、迁移和入库判断。

如果骨架来自快速检视，输出时要说清楚“这是暂定骨架，后续读到更多文本会修正”。不要把初版骨架包装成确定结论。

## 1. 书籍介绍

先帮助用户知道“这本书是什么”，再问要不要读、怎么读。

输出：

- 基本信息：书名、作者、版本、出版或写作背景
- 一句话简介
- 内容简介：几句话说明主要内容，不展开到章节级
- 核心问题
- 适合谁读
- 不适合期待什么
- 可能价值

书籍介绍是轻量入口，不是完整总结。它可以包含内容简介，但不替代检视阅读。

后台判断书籍类型，前台不要强迫用户理解“实用书、理论书、哲学书”等术语。

产物：

- 更新 book note 的 `Book Intro`

前台输出不能只停在一句话简介。书籍介绍之后，应立刻给出轻量检视结果，至少包括目录摘要和初版骨架，再让用户选择怎么读。

## 2. 用途确认

书籍介绍后，问：

> 你想怎么用这本书？

常见选项：

- 帮我读懂
- 帮我挑重点
- 围绕我的问题读
- 先整理进书库
- 这本先不读

如果用户选择不读，只归档或 pass，不进入共读。

产物：

- 更新 `Reading Intent`

## 3. 检视阅读

如果用户想继续读，再做检视阅读。目标不是完整总结，而是让用户看见结构和路线。

输入优先级：

- `chunk-index.md`
- 标题和副标题
- 目录
- 前言、序言、引言
- 结论、后记
- 关键章节的开头和结尾
- 必要时快速翻看全书

如果文本很长，只抽样读取关键位置，不追求一次性完整理解：

- 开头 1-2 个分块
- 目录或章节标题附近的分块
- 前言、引言、结论、后记对应分块
- 每个大部分的开头和结尾分块
- 用户目标相关的关键词命中分块

检视阅读的产物默认是**初版骨架**。它的价值是帮助用户选择读法，而不是替代全书阅读。

输出：

- 原始目录：用于定位和溯源
- 骨架地图：用更少层级说明主线、部分关系和推进方式
- 核心问题
- 章节价值：主干、案例、背景、补充、可跳读
- 阅读建议

这些内容必须同时进入聊天正文和 book note。聊天正文可以更短，但不能省略“目录/目录摘要”和“骨架地图”。

骨架地图是理解主视图，原始目录是定位视图。骨架可以先做轻量版本，后续共读中持续修正。

如果用户要求更高可靠性，进入**全书索引模式**：顺序扫完所有分块，生成 chunk summaries，再更新章节摘要和校准骨架。这个过程会消耗更多 token，但后续共读和总结会明显省 token。

产物：

- 更新 `Reading Map`

## 4. 确认读法

用户看完书籍介绍和检视结果后，再确认读法。

前台选项：

- 带我从头读
- 帮我挑重点
- 围绕我的问题读
- 先整理进书库
- 这本先不读

后台映射：

- 带我从头读：逐步共读 / 分析阅读
- 帮我挑重点：选段精读
- 围绕我的问题读：问题导向读 / 主题阅读
- 先整理进书库：资料读 / 归档
- 这本先不读：淘汰读 / 暂存

如果用户选择深读、问题导向读或长期资产化，再问：

- 你最想让这本书回答什么问题？
- 你希望最后留下什么？笔记、流程、主题卡、想法卡，还是判断？

产物：

- 更新 `Reading Plan`

## 5. 正式共读

共读目标不是章节摘要，而是帮助用户理解结构、判断观点，并形成自己的想法。阅读单元可以是问题块、观点块、论证、方法或章节片段。

长书共读时，每次只读取当前单元相关的 1-3 个分块。读完后先把作者观点、论证、例子、用户回应和入库建议压缩进 wiki，再进入下一个单元。不要在同一轮对话里连续展开太多原文。

正式共读的上下文预算：

- 必带：阅读意图、全书骨架、当前部分摘要、当前单元摘要。
- 可选：1-3 个原文分块。
- 尽量不带：已经读过但和当前问题无关的原文。
- 每轮结束：把讨论结果写回 stack 和 wiki，释放对原始上下文的依赖。

每个阅读单元：

1. 说明它在全书骨架中的位置，或它正在处理的问题。
2. 回答三问读解卡。
3. 把第四问抛给读者。
4. 停下来等用户回应。如果用户明确跳过讨论，记录为 skipped。
5. 用户回应后，记录用户观点，再补充 AI 判断或共同结论。
6. 写入 wiki 和 stack 后，这个单元才算完成。
7. 询问是否进入下一单元。

### 单元完成闸门

一个阅读单元必须经过“提问 - 等待 - 记录 - 再推进”，不能由 AI 单方面完成。

未满足以下条件时，不得进入下一单元：

- 已展示三问读解卡。
- 已提出一个具体、可回答的问题。
- 用户已经回答、修改、反驳，或明确说“跳过/继续”。
- 用户观点已经和作者观点、AI 判断分开记录。

禁止行为：

- 总结完就说“下一章建议读……”，但没有等用户讨论。
- 在同一次回复里既提问，又继续推进大量后续内容。
- 把“我猜用户可能会这样想”写成用户观点。
- 只更新附件或 wiki，不在聊天中完成提问和等待。

三问读解卡：

- 它在解决什么问题？
- 作者给出的答案是什么？
- 这个答案凭什么成立？有哪些论证和例子？

第四问抛给读者：

- 这可能和你有什么关系？

AI 可以提供可能连接，但不能替读者决定意义。

### 提问规则

- 每个阅读单元只问一个主问题，必要时最多追问一次。
- 不问空泛的“你怎么看”。
- 问题服务阅读目标：读懂、判断、应用或入库。
- 如果用户回答很短，顺着他的回答追问；如果用户不想讨论，记录 skipped 并继续。
- AI 可以给 2-3 个可能方向帮助启动，但用户负责选择、修正或否定。
- 提问后必须停下来。除非用户已经回答或明确跳过，否则不要进入下一单元。

### 提问路由

- 概念或定义：问理解问题。
- 作者主张：问判断问题。
- 论证过程：问证据问题。
- 方法或步骤：问应用问题。
- 案例或故事：问它证明了什么。
- 长期可复用观点：问入库问题。

可用问法：

- 结构：如果拿掉这一块，全书会少掉什么？
- 理解：如果用你自己的话讲一遍，你会怎么说？
- 证据：作者的例子到底证明了哪一步？
- 判断：这个观点在哪些条件下成立，在哪些条件下可能失效？
- 迁移：它可能改变你的工作、学习、写作或项目里的哪一步？
- 入库：它应该留在本书笔记里，还是变成主题、想法、方法或计划？

不能只总结完就宣布结束。没有用户回应或明确跳过时，这个阅读单元不得标记为完成，也不得推进下一章。

## 6. 总结与入库

读完一个阶段或一本书后，先收束理解，再分流资产。不要把总结全部丢给用户，也不要由 AI 单方面决定个人意义。

分工：

- AI 负责整理、压缩、分流：作者观点、结构、论证、可复用概念、方法、摘录、入库建议。
- 读者负责确认意义：真正收获、同意或怀疑、个人连接、是否值得重读、未来是否复用。

流程：

1. AI 给出总结入库草案。
2. 读者确认、修改、删除或补充。
3. AI 把确认结果写入 wiki。
4. 只保存未来会被调用的内容。

总结入库草案：

- 这本书或这一阶段的核心问题
- 作者的核心答案
- 作者最重要的 3-5 个观点
- 建议写入 book note 的内容
- 建议新建或更新的 theme card、idea card、method card、reading plan
- 可能值得保留的摘录
- 2-3 个读者确认问题

默认确认问题：

- 哪一条最像你真正的收获？
- 哪一条你不同意、想删掉或想改写？
- 有没有一个你想以后继续追的问题？

## 最小启动方式

当用户说“按 Book Wiki 读这本书”或类似表达时：

1. 读取本 workflow
2. 导入材料
3. 输出书籍介绍
4. 询问用户想怎么使用这本书
5. 如果继续读，做检视阅读，输出目录、骨架地图、核心问题、章节价值和阅读建议
6. 确认读法
7. 开始共读、讨论、记录和入库分流
